# 视频资源实验的短时照片后台维护

本工具只用于固定 8d3e637 线上版本及固定 8c8a417 实验输入。上次正式三次内存预检不足 1280 MiB，没有创建容器；不得反复等待高点或降低门槛重跑。只读观察发现原照片后台使用约 34 MiB，可在明确维护窗口中让它排空当前工作后暂停，再执行原 384/768 MiB 隔离实验。这个运行条件变化必须写入验收结果。

协调者须审查此工具及固定输入后明确运行一次：

```text
python3 -B media_video_resource_window.py --output /tmp/family-dashboard-media-ipc-probe/resource-window-<全新批次>
```

工具持有两个既有发布锁，核定原四个容器、源码和私有配置摘要，要求备份 timer active、备份服务 inactive。只暂停 timer，随后再次确认没有备份触发竞态；不终止运行中的备份。照片后台仅按原不可变容器 ID 使用 `docker stop --signal SIGTERM --timeout -1`，原进程处理完当前 tick 后退出。没有强杀超时；观察超时也不得启动第二个 stop。此语义见 [Docker stop 官方说明](https://docs.docker.com/reference/cli/docker/container/stop/)。

应用、网页、日历同步保持原进程。工具依次运行 `worker100`、`response64`，各自继续执行原三次 1280 MiB 预检和压力中止策略。首个失败就不执行第二个，不改变参数或重试。所有新容器与合成数据都由已审实验工具建立，不能使用生产数据卷。

正常或实验失败后，只有全部已知实验容器确实停止、没有未知创建结果、原源码／配置／四个容器身份仍一致时，才 start 原照片后台 ID。工具记录三次进程状态检查并恢复原 active 备份 timer。它不重建容器、不换镜像、不迁移或恢复数据库、不启动额外备份、不操作其他项目。照片后台没有独立健康检查或持久 heartbeat，因此结果只证明原进程恢复，不能宣称已验证一次真实导入或 worker tick。

若 stop 的原结果不明确、实验结果缺失、实验容器还运行、原容器或配置变化，自动恢复将被拒绝并保留证据。应由协调者检查原句柄和固定 ID，补齐当前状态后制定具体恢复步骤，不能重放整个维护命令。媒体暂停期间，新选片会等待后台恢复处理。

Docker inspect 的原环境只在进程内比较，证据仅保存配置摘要及必要状态；不将 inspect stdout、密钥、数据库、照片或视频提交 Git。此维护实验验证隔离流程与 cgroup 上限，不证明生产峰值并发容量或真实电视播放。
