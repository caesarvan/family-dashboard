# 本人订单来源与库存

这是源码候选的操作与接缝说明。是否部署、真实浏览器和生产验证由本批发布验收记录说明；本页不代表已上线。

## 使用

1. 在「家庭资金 → 本人账本」打开一笔本人订单，选择「登记或查看订单库存」。原月份、搜索和分页在内存中保持；返回原订单时重新读取本人交易和账本。
2. 明确选择一个商品。已关联的行可以直接查看其当前可读批次；无法核对的关联不会显示隐藏库存 ID，也不会鼓励重复登记。单行订单也需要明确选择。
3. 选择已有物品，再使用已有的本人登记批次，或添加新采购批次。也可以选择「用此商品新建私人物品」：名称、规格带入可编辑草稿，单位留空，默认仅本人可见。金额、订单号、账户、付款或来源备注不会复制到库存。
4. 手动填写计量单位及批次数量。原订单数量如“两盒共六节”只供阅读，不换算单位、不推定实收。新物品保存后进入空数量批次草稿；保存批次是独立操作，取消后续来源关联也会保留物品和批次。
5. 在已保存批次选择「关联这件订单商品」，核对「预览关联订单来源」，再「确认关联订单来源」。如稍后继续，可从原订单重新选择商品，再选择已经保存的物品和批次。
6. 返回库存批次后，沿用「收货」明确填写实际到货数量。关联来源不会收货，不确认付款／退款，不改变财务支出、采购完成状态或金额。

批次详情中的「查看本人订单来源」只对采购批次登记人显示。共享库存允许家人按已有权限管理实物，私人订单来源仍只能由其本人查看。本人可预览并明确解除来源；原订单变更或删除时显示「待核对」，不会改动已有实物记录，也不会静默重映射商品行。

## 失败与恢复

- 保存物品／批次继续使用既有原 `requestId` 与库存回执。来源关联使用独立编号，不能因关联失败而重新创建物品或批次。
- 来源确认结果不明时保留原编号和签名令牌，显示「核对原来源操作」，阻止离开。先 GET 原回执；若未找到，重新核验库存访问后只重试原始确认内容。已取得有效回执后，后续刷新失败不会重新发送确认。
- 过期预览或版本冲突要求重新读取、重新预览和明确确认。已保存的物品／批次保留。
- 身份变化、撤权、后台或离线隐藏私人内容。返回前台后重新检查完整身份与当前权限；未知操作保留原恢复信息，不跨身份显示。
- 原订单删除不阻止已有来源在批次内明确解除。订单入口本身显示不可用，库存仍可从家庭物品打开。

## 前端接缝

- `FinanceScreen.tsx` 嵌入 `InventoryScreen`，只传本人订单 ID；原查询与详情仍由财务工作区持有，不把私人资料放入路由参数或家庭共享状态。
- `InventoryScreen.tsx` 读取有界订单行、复用手动物品／批次流程；`InventorySourcePanel.tsx` 负责来源查看、预览、确认、原回执恢复与生命周期边界。
- `inventorySources.ts` 校验来源 DTO、目标 ID、revision、行选择、能力、预览及回执；新字段使用明确白名单重建。`inventory.ts` 将服务端已有 `canManageSources` 纳入批次类型和校验。
- `HouseholdApp.tsx` 将财务内嵌库存纳入既有导航阻止；没有新增全局路由、依赖或浏览器存储。
- 来源使用 `/inventory/orders/:id`、`/inventory/acquisitions/:id/source`、`/inventory/sources/preview`、`/inventory/sources/confirm` 和原 `/inventory/operations/:requestId`，具体 HTTP 契约由 API 文档维护。

## 本地验证

`node --experimental-transform-types --test frontend/tests/inventorySources.test.mjs frontend/tests/inventoryFollowup.test.mjs` 使用合成数据执行真实 TSX、DTO 校验器与 InventoryFence，界面 hooks、Paper 和 HTTP 是明确测试替身。覆盖预览取消、确认、丢失／异常回包、原回执无第二次写入、过期／冲突、来源删除后解除、后台与身份变化以及既有售后流程。此类测试不等于浏览器布局、真实 HTTP／SQLite、云服务或生产验收。

执行 `node frontend/node_modules/typescript/bin/tsc --project frontend/tsconfig.json --noEmit` 检查完整前端。真实浏览器及后端组合在集成候选独立执行。
