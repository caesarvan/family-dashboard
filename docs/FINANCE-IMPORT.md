## 实际支持与核对边界

本版补齐现有本地订单表的两种表头：淘宝订单在既有日期列缺失时识别“订单提交时间”；拼多多订单识别“商品名”，仍优先使用既有可靠标题列。仅对明确选择的来源与 orders 类型生效，不新增实付金额推断。现有淘宝表尚未证明属于官方原生导出，拼多多表匹配本地扩展格式；合成测试不等于真实文件全量验收。

| 内容 | 当前行为 |
|---|---|
| 支付宝、微信账单文件 | 读取常见中文列名的 CSV / 无宏 XLSX，来源由用户明确选择 |
| 淘宝、拼多多订单文件 | 读取具有可识别列名的文件，订单金额单独统计，不重复计入支付支出 |
| 通用模板 | 通过界面下载 CSV；必须明确币种 |
| 多工作表 XLSX | UI 在名称留空时先列出工作表，选定后读取；手填准确名称直接读取。旧 API 默认仍读取首个可见表，不自动合并各表 |
| CSV 编码 | 自动模式先严格 UTF-8 解码，失败后尝试 GB18030；可手动指定 |
| 退款与资金划转 | 独立退款才抵减支出；原消费的退款状态不自动反转全额；转账、充值、还款、理财划转单列 |
| 订单、付款和退款核对 | 提供本人同币种候选与原始编号理由；本人确认后按金额关联，支持撤销与部分退款 |
| 跨文件相似支付 | 不凭金额/日期自动合并；本人确认重复后排除重复统计，保留原始记录 |
| 预算 | 本人、月份、币种和分类维度；与同口径的已导入消费减退款比较 |
| 投资 | 机构、产品、币种、数量、成本、估值与核对日期的手动记录与整理表预览／确认，无实时行情与自动账户连接 |

测试使用合成 OOXML、UTF-8 / GB18030 文件和常见中文表头，**不能据此声称所有平台、银行、导出版本均已验证**。真实导出格式变化时，先核对预览；未识别的文件可按通用模板整理。

投资汇总按币种分别显示。当前持仓盈亏为已估值项目的估值减成本，不包含分红、已实现收益、税费和汇率影响。估值留空时保留“待估值”。投资列表不与历史资产基线自动相加，避免重复计算。

## 投资持仓整理表

从“投资账户”进入持仓导入，为实际账户填写稳定来源名称，下载虚构模板或“当前持仓整理表”，核对后上传 CSV／无宏 XLSX。使用固定英文列，不承诺直接识别任意银行、券商原生文件。已有手工记录使用当前表里的 `recordId` 明确关联；同机构不同账户应使用不同来源名称。

| 方法 | 独立持仓接口 | 用途 |
| --- | --- | --- |
| GET | `/api/finance-hub/investments/imports/template` | `mode=sample` 下载虚构示例；`mode=current&sourceName=...` 下载该来源及未关联的本人持仓 |
| POST | `/api/finance-hub/investments/imports/preview` | 提交 `{sourceName,file,inspectSheets?}`，检查逐项新增／更新／不变和错误 |
| POST | `/api/finance-hub/investments/imports/confirm` | 仅提交 `{previewToken}`，明确确认整批保存；不重复传文件或客户端金额 |

XLSX 未选工作表时自动只发现名称，选表后才校验持仓；发现状态没有确认凭据。金额使用小数点，允许完整三位千分组，如 `1,234.56`；`1,23`、错误分组、两种逗号混用、货币符号和科学计数法均拒绝。原币种整数分保存，未知估值不当作零，不自动换汇。

持仓预览凭据有效 15 分钟，规范化快照在服务端短期保存；它与既有账单的无状态签名不同。任一错误阻止整批确认；预览后本人持仓或关联变化需重新预览。确认保存四表中的来源、稳定关联和业务回执；完整表结构见 [数据模型](DATA-MODEL.md#投资持仓导入四表)。文件遗漏行不等于清仓，删除后的关联保留，历史回执重放不恢复已删除持仓。

原附件不保存，暂存快照／会话摘要不进入个人 ZIP；仅本人业务来源、关联和回执按 [导出白名单](PORTABILITY.md#投资导入历史) 输出。持仓仍是私有投资记录，不进入公共荷包、消费流水或历史资产基线，也不触发银行／行情／云端调用。细节、错误与模板保护规则以 [投资导入专文](INVESTMENT-IMPORT.md) 为准；[专项测试](../tests/test_investment_import.py) 仅使用合成输入，不作为真实机构格式或生产导入验收。

## 使用步骤

1. 打开“财务中枢 → 导入数据”，选择文件来源和记录类型。
2. 选择 CSV / TXT / XLSX。CSV 默认自动识别编码；XLSX 流程可留空名称后先选择工作表，也可手填准确名称直接读取，详见下一节。
3. 有多个金额候选时先明确选择一列，再查看预览中的实际编码、工作表、日期、标题、金额、币种、收支方向与重复计数。
4. 说明页或空表不是账单时换选有效工作表；选定表包含公式或错误值时仍拒绝读取。有业务错误行时修正整个文件再导入。
5. 确认后保存到本人账本。确认后显示完成回执并定位实际月份；跨月可以直接切换对应月份。重复文件不会重复入账；同编号金额／日期变化保留旧记录并报告冲突。读取当前账本失败时保留成功回执，只重试读取。
6. 逐笔核对确属共同消费后，才标为共享。伴侣仅能看到已确认的共同消费汇总，不能看到账号、交易标题或私人投资。
7. 在“账单与订单 → 核对 → 关联与对账”查看候选，按原文件确认订单/付款/退款关系或重复支付。分配金额可小于原金额，确认前会显示统计影响；关系可撤销。

原始文件只在本次请求中读取，内容不写入日志，也不作为附件存储；数据库保存标准化记录及导入批次。预览不写入账本，签名有效期 20 分钟，绑定当前用户、来源、类型、文件内容、编码和工作表选择。

新导入会另外保留 `merchantOrderId`（商户订单号/商家订单号/商户单号）、`paymentId`（支付交易号/支付单号/支付宝交易号/微信支付单号）和 `originalTransactionId`（原交易号/原交易单号/原支付单号）。通用 CSV 可直接加这三个可选列，最多各 160 字符。历史记录没有这些字段时，不凭记忆补齐，也不因重传文件覆盖旧记录；仍可通过标题、金额与日期查候选。

有原交易编号时，仍按同来源、类型、原编号和方向防止同笔重传。**无原编号**时按表格内容摘要和原行位置生成标识：同文件重传跳过；两行相同内容仍保留为两条，不把可能的真实多次消费自动合并。改动表格后重传可能产生新记录，应使用明确的重复核对。旧版已按内容合并的历史记录无法从当前数据库恢复，需回到原文件核对。

## 先选择 XLSX 工作表

本节流程已于 2026-09-15 06:50:21 发布。导入表单提示“留空先选择工作表”：选择 XLSX 且名称留空时，先显示“选择账单工作表”；填写准确名称时保留直接读取该表的行为。CSV 不增加选表步骤。

1. 从名称列表选一张账单表。列表可以包含隐藏表、说明页、空表或公式表，仅表示名称可读取；“待选择 / 待预览”不代表无交易或没有错误。
2. 选表后才校验表格。多个或同名金额列仍需按列位置选择；唯一金额列会显示实际来源列。
3. 说明页、空表、公式或错误值导致失败时，名称列表仍在，可以换表或点击“读取所选工作表”重试。公式不会执行，缓存值不会作为账单；需要该表时请先在本机修正或另存为纯值。
4. 换表立即清除旧金额选择、预览行和令牌，禁用确认。新预览完成且无错误后，再点击“确认导入 · 仅本人”。不会自动读取其他表并入账，也不会合并所有表。

包损坏、宏、外链、路径穿越、加密或超限仍会直接拒绝，不会把这类错误转成可选名单。发现阶段检查整个包的 XML 结构和安全边界，财务单元格内容仅在选表后校验。名称列表和原文件只存在于当前请求与页面，不作为附件保存；切换成员、家庭或原表单后不沿用旧结果，迟到响应不会覆盖新输入。

接口使用 `inspectSheets:true` 获取元数据，选表后移除该字段及旧金额选择，重新正常预览；发现模式没有有效令牌，不能确认。严格类型、签名及响应字段见 [XLSX 工作表名称发现](FINANCE-API.md#xlsx-工作表名称发现)。未使用发现参数的旧 API 仍读取首个可见表；因此直接调用旧格式遇到说明页时，仍应明确指定有效工作表。

## 文件与安全限制

- 文件最大 **2 MiB**；既有账单／订单 preview 和 confirm 接口接受最大 3,000,000 字节 JSON 请求，以容纳 Base64。持仓 preview 也使用此请求上限，持仓 confirm 不传附件。
- CSV 最多 5,000 条业务记录，转换后的 UTF-8 表格文本最大 2 MiB。
- XLSX 总展开内容最大 **8 MiB**、128 个内部文件、20 张普通工作表。选定表最多 **5,000 行（含表头）**、80 列、100,000 个实际单元格。
- XML 限深度 48、每部分 300,000 节点，只接受 UTF-8 XML；在解析前拒绝 DTD / ENTITY，不能用 UTF-16 绕过检查。
- ZIP 不落盘解压；同时检查原始及标准化文件名，拒绝路径穿越、重复名、链接及未知压缩格式。
- 所有关系文件拒绝外部资源；实际宏、二进制部件、嵌入对象和宏 `Override` 声明仍拒绝导入。独立候选只例外处理下述未使用的默认声明。
- 新增发现模式还检查包内全部 XML 部件（扩展名不区分大小写）的编码和结构；返回名单不意味着其中每张表的公式、错误值或金融列已经通过校验。
- 选定工作表含公式或错误单元格时拒绝；不执行公式，也不使用公式缓存作为账单证据。
- 不支持加密工作簿、旧版 `.xls`、`.xlsm`、`.xlsb`。请在本机解密或另存为无公式、无宏 XLSX / CSV。
- 每个进程只允许一个文件解析；忙碌返回 429，失败路径释放解析槽。照片解码有自己的现有限流。

Excel 已将超长交易编号保存为数值并丢失精度时，导入器无法恢复原编号。优先使用原始文本编号，核对预览与原账单；不应靠猜测修补。

### 未使用的二进制默认声明兼容修订（独立候选，尚未发布）

部分纯值导出文件在 `[Content_Types].xml` 中保留了 `Default Extension="bin"`、类型为 `application/vnd.ms-excel.sheet.binary.macroEnabled.main` 的声明，却没有任何 `.bin` 部件。[微软的 OPC 内容类型说明](https://learn.microsoft.com/en-us/visualstudio/extensibility/the-structure-of-the-content-types-dot-xml-file?view=visualstudio) 将 `Default` 的类型与文件扩展名关联。候选 reader 仅在正确的 OPC namespace、精确属性、无子节点或文本内容且全包不存在 `.bin` 部件时容许这一已知声明；不会读取、解析或运行宏。

实际二进制文件（包括空文件及大写 `.BIN`）、任何宏 `Override`、其他宏默认声明继续拒绝。外部关系、嵌入对象、恶意 XML、公式及缓存值的原有限制保持；工作表发现仍不等同单元格预览通过。

第一阶段的本地只读预演保留为历史：只修正默认声明时，一份淘宝文件的 394 条非空表格行中 299 行可解析，95 行校验错误，整体没有确认令牌。后续结构检查证实这 95 行是六列明确合并范围内的商品续行；下面的独立分组候选处理这一已证实结构，不补造日期或金额。

### 淘宝明确合并订单组（独立候选，尚未发布）

仅选择 `source=taobao`、`kind=orders` 的 XLSX，且首行精确为「订单号、订单提交时间、订单状态、店铺名称、商品名称、商品链接、型号款式、商品数量、商品金额、实付金额、运费」时，才识别本格式。订单号／日期／状态／店铺／实付／运费六列（A/B/C/D/J/K）的合并跨度必须一致；单项订单可以混排。错位、重叠、越界、缺少组首字段、续行出现冲突值或孤立缺日期行均拒绝，不按相邻行前向补填。CSV、其他来源和其他表头仍走原逐行规则。

预览每个订单显示一行，金额只取组首 J 列「实付金额」一次，商品金额不触发额外金额列选择。摘要用首项名称及明细条目数；「N 项商品」不是购买数量合计。完整 `orderItems` 与 `orderGroup` 保留每件商品的名称、规格、数量原文、商品金额原文、链接原文、原工作表行号和运费原文，字段见 [API 明细契约](FINANCE-API.md#淘宝合并订单明细候选契约)。这些文本不做金额分摊、退款推断或链接访问；含币种警告时仍需按原单据核对。

新分组输入按本人、来源、类型和原订单号查找已有订单。相同订单跨文件改变状态／方向、日期、实付金额、币种或商品业务明细时，预览标记 `conflict`，确认跳过并保留旧记录；旧订单没有商品明细也不自动补写。仅移动工作表行位置、改文件名不构成内容冲突。已有同订单号的多条历史记录会报告冲突，不新增、不合并、不迁移；其他来源与普通 CSV 的既有去重方式不变。

本次实际原文件仅在本机临时预览：淘宝解析为 **299 个订单、394 条商品明细、0 条错误**，其中 252 单方向待核对、47 单排除；拼多多仍为 910 条、0 条解析错误，其中 892 条待核对、18 条排除。两份文件均没有币种列，CNY 是未经独立核实的国内平台默认值；订单和退款状态不证明已支付或已退款。原文件 SHA 前后不变，没有确认真实入账、外网访问或生产写入；结果不代表其他导出版本已兼容。

商品明细只属于本人。个人 ZIP 的 `data.json` 保留完整明细，CSV 副本仍每个订单一行汇总，不展开商品；共同消费汇总、电视、采购投影不带商品字段。合成回归见 [test_taobao_order_groups.py](../tests/test_taobao_order_groups.py)。

## 接口契约

`POST /api/finance-hub/imports/preview` 与 `POST /api/finance-hub/imports/confirm` 使用成员会话及 `X-CSRF-Token`，电视不能访问。新格式：

```json
{
  "source": "wechat",
  "kind": "payments",
  "file": {
    "name": "账单.xlsx",
    "contentBase64": "这里替换为文件字节的标准 Base64",
    "encoding": "auto",
    "sheet": "支付账单"
  }
}
```

`source` 为 `generic` / `alipay` / `wechat` / `taobao` / `pinduoduo`；`kind` 为 `payments` / `orders`。`sheet` 可省略或留空；`encoding` 为 `auto` / `utf-8` / `gb18030`，仅影响 CSV。

原有 `{source, kind, csv: "..."}` 文本格式继续可用。`csv` 与 `file` 不能同时提交。

预览返回 `rows`、`errors`、`errorCount`、`warnings`、`newCount`、`duplicateCount`、`conflictCount`、`totals`、`previewToken`、`expiresInSeconds`，并增加 `fileInfo`：

```json
{
  "format": "xlsx",
  "name": "账单.xlsx",
  "encoding": "OOXML / UTF-8",
  "sheet": "支付账单",
  "sheets": ["支付账单", "订单"],
  "worksheetRows": 3,
  "note": "仅导入所选工作表的纯值；请核对原始编号。"
}
```

确认时发送**同一份完整正常预览请求**并附加 `previewToken`。修改文件、工作表、金额列、来源或编码后必须重新预览；显式 `inspectSheets` 也参与签名，确认时不能擅自增删。`inspectSheets:true` 无论是否附有签名都拒绝确认。确认结果保留 `imported`、`duplicates`、`conflicts`，已增加 `confirmedAt`、`resultMonths`，详见[导入确认回执](#导入确认回执与实际月份)。现存同指纹记录不再次插入；已经删除的记录不在此去重集合中。

错误为 `{ "error": "可读说明" }`：未登录 401、成员权限 / CSRF 403、输入或格式错误 400、请求体超限 413、解析忙碌 429。无效格式和失败事务不会部分入账。

### 导入确认回执与实际月份

确认成功响应增加两个字段，以下为虚构的单月示例：

```json
{
  "imported": 1,
  "duplicates": 0,
  "conflicts": 0,
  "confirmedAt": "2026-09-15T06:00:00+00:00",
  "resultMonths": [{"month": "2026-08", "recordCount": 1}],
  "note": "导入仅保存到本人账本。未修改公共余额；编号冲突的旧记录保持原值，请在原文件核对。"
}
```

- `imported/duplicates/conflicts` 沿用原有逐行统计，冲突属于重复中的保留原值情况。
- `confirmedAt` 是服务端完成这次确认响应的时间，不是交易发生日期，也没有新增持久化回执表。
- `resultMonths` 按本次确认涉及且实际保留的唯一指纹记录统计，月份倒序；同一记录在文件重复出现只计一条。全重复文件仍返回现存记录月份；冲突保留原日期，因此可能与当前上传文件中的月份不同。
- `GET /api/finance-hub/overview` 的 `availableMonths` 是当前本人全账本的现存月份；它比本次确认的 `resultMonths` 范围更大，也可能因后续删除而变小。两者都不是预览拟新增行清单，不应与净消费计数混用。

界面确认后显示“导入确认已完成”，单月直接打开该月账本，跨月给出各月按钮。当前月空但其他月份已有记录时，概览提示已有记录并提供月份入口，不再要求导入第一份账单。回执的月份／条数表示确认时的历史结果，折叠说明解释它与当前账本的差别。

已经收到成功确认响应后，即使后续 `/me` 或 overview 读取失败，原流程保留成功状态，“重新读取账本”只发 GET，不再次发送 confirm。若记录此时已被删除，读回显示当前没有记录，不自动恢复它。关闭或新建页面后，迟到成功／错误不能接管新草稿；原成员、家庭、CSRF 与服务端会话检查不一致时清除旧内容。

**没有收到确认成功响应**属于另一个状态：原预览允许本人明确使用原负载重试，后端仍按现存指纹去重。它不是投资导入或消费观察所用的持久化回执协议；记录删除后再明确提交原账单可重新入账，不能承诺旧令牌永远不再写入。无自动重发、无后台文件保留或自动导入。

专项入口：[API 测试](../tests/test_finance_import_navigation.py)、[浏览器测试](../tests/browser_finance_import_navigation_check.py)。测试采用临时合成数据，不证明真实机构导出已经接通。
