# 日历发布的当前会话边界

本页描述从 `f48c02dc51b6610a1f2af20a3b8dbc44286efda7` 开始的候选修复，尚未合并或发布。接口 DTO 沿用 [日历发布契约](CALENDAR-PUBLISH.md)，实现仅修改 [calendar_publish.py](../calendar_publish.py)，不修改 schema、公共会话模块、账号锁顺序或 worker 的持续发布授权。

## 修复的窗口

请求入口的 `require_member()` 只代表当时身份有效。此前在取得账号锁或等待 SQLite 写事务期间，另一连接可以撤销会话；`confirm_locked` 及发布操作仍使用旧 `g.actor`，使撤销后的请求继续入队。原基线的真实临时 SQLite 复现返回了 `200 queued`，而预期是 401，失败原件保留。

模块内 `revalidate_member` 复用 `member_sessions.current`，核对当前凭据、成员、`auth_version` 与家庭。首次／重复确认以及 retry、pause、resume、冲突确认、时间复核确认，都在原 `BEGIN IMMEDIATE` 获得写锁后再次校验；拒绝时回滚，不改变队列、实体、审计或全局版本。

两个远端预览在取得账号锁后、提供方准备完成后、远端读取返回或抛错后，分别用短连接复核身份。远端读取期间不持有数据库写事务；已启动的请求不能撤回，但失效身份不会收到远端内容或预览令牌。状态读取、本地预览及授权链接也在形成响应前复核；OAuth state 本身继续使用原有事务内认证上下文检查。

账号锁目前是非阻塞进程锁，忙时拒绝；本修复覆盖取得锁后的身份变化及真实 SQLite 写锁等待。读取的最终复核使用新连接，不依赖先前 SQLite 快照中的会话状态。任何最后校验之后的撤销都不能收回已经送出的响应。

## 已提交操作与持续授权

写操作提交后另做当前会话检查。若此时发现撤销，返回 401 并隐藏响应，**不撤回已提交队列**。本人重新登录后，应先读取原旅行发布状态；首次确认使用原确定性发布标识，再次确认不会建立第二条同目标记录。401 不应被客户端解释成“保证没有执行”。

退出本地登录不会自动撤销过去明确确认的持续发布授权，worker 仍可处理原队列；停止发布仍须使用原暂停流程。远端 OAuth scope、编辑权、ETag、发布标记及时间复核语义保持原样；没有增加邀请、参与者或删除云端事项的操作。

## 验证范围

[专项测试](../tests/test_calendar_publication_session.py) 使用两个真实提供方适配器、模拟云端 HTTP 和独立临时 SQLite。第二连接实际撤销会话或提升 `auth_version`，覆盖首次／重复确认、retry／pause／resume、两种确认、两种远端预览、迟到状态／令牌／授权链接、提交后隐藏响应及重新登录读回。另有线程与真实 SQLite writer 竞争，验证请求等待期间已提交的撤销；worker 用例验证先前持续授权不随登录退出消失。

测试不读取真实家庭数据、不访问 Microsoft／Google，不证明本人真实日历发布、实际设备或生产部署通过。本专项 58 项与原日历发布、旅行时间复核、旅行事务身份共四模块实际 115 项通过，零失败／错误／跳过（79.04 秒）；专项已包含在 115 项中，不相加。原先 54 项专项与当前结果有重叠。私有原件为 `test-results/calendar-session-before.xml`（修复前 1 失败）、`calendar-session-fixed.xml`（初版 54 通过）和 `calendar-session-regression.xml`（最终 115 通过），不入 Git。
