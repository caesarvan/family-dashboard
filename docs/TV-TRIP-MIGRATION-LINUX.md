# 电视旅行回顾 75 → 77 迁移演练

`deploy/tv_trip_migration_linux_probe.py` 准备固定 Git 输入，并在单个不可变应用镜像中分阶段演练合成数据库的迁移、重启和完整恢复。沿用现有无网络、只读源码、非 root 应用进程的演练方式，不挂载生产数据，不启动同步或媒体 worker。

当前 `BASE` 为 `88f7e3628756e4e961b43513d3de44c9d7e96dcd`，只包含已冻结的新表初始化器及迁移器。此版本尚未组合完整电视旅行 API，必须在 API 冻结后更新固定基线并重新验证；不能把此版本通过当作最终发布准入。

历史应用来自实际部署源 `e8f0427b35157074d179bc4de86a7c5c4db0a755`。用真实 Flask 初始化、成员与任务接口建立两户三库 75/9，再写入合成财务、路线、提醒、媒体与播放记录。旧表结构来自实际历史应用，不复制 DDL 或通过删除新表伪造旧版本。

## 阶段

1. `verify`：核对镜像根模块、requirements 字节和 UID 10001。
2. `seed`：创建两户三库和旧表哨兵；第二台电视及其旧播放行也在此时加入。
3. `migrate`：实际完整备份并调用 75→77 迁移器。
4. `startup`：候选应用仅初始化；不运行服务器或后台任务。
5. `check`：核对所有旧表、行、设置、序列和触发器保留，新两表为空。
6. `rollback75`：使用部署文档原恢复算法恢复完整三库至新目录，核对 75/9。
7. `partial`：第二户数据库改为 0400，在 UID 10001 下实际拒绝写入；验证第一户 77、第二户 75，拒绝重放，再完整恢复。
8. `populate77`：每户插入两条旅行选择和三条幂等回执，包含旅行失效、开始者缺失与设备不存在的记录。仅修改两张新表，其余表严格不变。
9. `restart`：实际应用再次初始化，非空新表应保留。
10. `restore77`：备份并完整恢复非空 77/9，逐项核对库组内容。

这些记录是存储保全夹具，不代表用户操作或真实媒体播放。生成程序保留所有原件和每阶段输出；输入变化和同目录重试被拒绝。

## 调用与证据

`prepare --repo --commit --output-dir` 只接受固定 BASE 加本工具、测试与本文；输出必须为新目录。`verify --bundle --input-sha256` 只读核对全部输入。`run --bundle --input-sha256 --image-id --output-dir` 要求 Linux root 使用 `python -B`，另行实际创建受限容器。

容器为 network none、根只读、UID/GID 10001、cap-drop ALL、禁止提权、1 CPU、384 MiB 内存、128 pids。只有合成 data/proof 目录可写，仅清理本次返回的容器 ID。工具不接受可变镜像标签，不执行 Compose，也不接触生产挂载。

本地测试的八段真实 Python/Flask/SQLite 流程跳过 Linux UID 和 0400 部分失败；它不能证明 Linux 镜像或生产部署成功。实际十阶段容器结果、完整功能浏览器验证和最终发布包须分别核对与记录。
